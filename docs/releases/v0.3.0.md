## Overview

v0.3.0 introduces the Execution Engine, a provider-agnostic task execution architecture that dispatches code generation work to AI coding agents. This release establishes the foundation for multi-provider AI code generation with a clean adapter pattern, structured contracts, post-execution validation, and comprehensive observability.

The execution layer sits below the existing engineering pipeline (Milestones 1 and 2) and provides the runtime infrastructure needed to execute generated task plans against real AI coding providers. The architecture is designed for extensibility: new providers can be added by subclassing a base adapter and registering with the provider registry, with no changes required to the execution engine itself.

This release also introduces a validation pipeline for post-execution code quality checks, structured logging with correlation ID propagation, health checks for provider readiness verification, capability validation to ensure providers support required task capabilities, and automated architecture boundary enforcement via AST-based tests.

## New Features

### Execution Engine

The `ExecutionEngine` class in `execution/engine.py` orchestrates the full task lifecycle:

1. Input validation — verifies task ID, title, description, and repository path are present.
2. Workspace creation — copies the source repository into an isolated UUID-named workspace directory.
3. Adapter loading — uses `AdapterFactory` to load the provider adapter without importing concrete adapter classes.
4. Capability validation — checks that the provider supports all capabilities required by the task.
5. Optional health check — verifies provider readiness before execution.
6. Task execution — dispatches the instruction to the provider adapter.
7. Result collection — gathers execution telemetry and output paths.
8. Validation — runs the validation pipeline against the workspace.
9. Report generation — produces an `ExecutionReport` with status, timing, errors, and correlation ID.

The `WorkspaceManager` class in `execution/workspace.py` handles isolated workspace creation and cleanup, with safety checks to prevent cleanup of directories outside the workspace base path.

### Provider Framework

The provider framework is built on three core components:

**ExecutionAdapter** (`execution/adapters/base.py`) — Abstract base class defining the provider contract:
- `prepare(context, project_dir)` — Set up workspace environment and contract/log paths.
- `execute(instruction)` — Execute a task instruction and return an `ExecutionResult`.
- `collect_results()` — Gather execution telemetry and output paths.
- `cleanup()` — Clean up ephemeral state while preserving logs and contracts.
- `health_check()` — Optional method returning a `HealthCheckResult`.

**ProviderRegistry** (`execution/adapters/factory.py`) — Class-variable-based registry supporting:
- `register_provider(name, adapter_class, capabilities)` — Register a provider with its capabilities.
- `get_provider(name)` — Look up a provider's adapter class and capabilities.
- `list_providers()` — List all registered provider names.
- `has_provider(name)` — Check if a provider is registered.
- `validate_capabilities(name, required_capabilities)` — Verify a provider supports required capabilities.

**ProviderScaffoldAdapter** (`execution/adapters/scaffold.py`) — Base class providing default implementations for all lifecycle methods except `execute()`. New providers can be added by subclassing this class and setting the `provider_name` class constant.

**AdapterFactory** (`execution/adapters/factory.py`) — Static factory that creates adapter instances and injects configuration with validation.

### Provider Implementations

**OpenHandsAdapter** — The only provider with a production `execute()` implementation. Handles:
- Contract generation with schema versioning.
- Configuration validation with specific error types (authentication, rate limit, configuration, execution).
- Structured logging on success and failure.
- File scanning to report modified files.
- Health checks covering configuration, authentication, workspace, and provider readiness.

Six scaffold providers are registered and fully functional for lifecycle operations (prepare, health check, collect results, cleanup) but raise `ProviderNotImplementedError` on `execute()`:
- ClaudeAdapter
- CodexAdapter
- DevinAdapter
- CursorAdapter
- VSCodeAdapter
- AntigravityAdapter

### Validation Pipeline

The `ValidationEngine` in `execution/validation/pipeline.py` runs a configurable list of `Validator` instances against the workspace after execution:

- **RuffValidator** — Runs `ruff check .` for linting.
- **RuffFormatValidator** — Runs `ruff format --check .` for formatting.
- **PytestValidator** — Runs `pytest .` for test execution.

Each validator produces a `ValidationResult` with success status, errors, output, and correlation ID. Individual validator failures are caught and reported without crashing the pipeline.

### Observability

**Structured Logging** (`execution/adapters/logger.py`):
- `ProviderStructuredLogger` writes JSONL log entries with schema-validated fields.
- Each entry includes timestamp, provider, model, task ID, execution ID, status, duration, error, and correlation ID.
- Log files are stored in `.ai/logs/{provider_name}.jsonl` within the workspace.

**Correlation ID Propagation**:
- Correlation IDs are generated at the engine level and propagated through adapters, contracts, and validation results.
- Backward compatibility ensures existing code without correlation IDs continues to work.

**Provider Activity Logging**:
- Plain-text log files in `.ai/logs/{provider_name}.log` capture provider-specific activity with timestamps and correlation IDs.

### Contract Schema

The contract system in `execution/adapters/contract.py` provides:
- `load_and_validate_contract(path)` — Loads a JSON contract file and validates its schema version.
- `SUPPORTED_SCHEMA_VERSIONS = {"1.0"}` — Currently supported schema versions.
- `DEFAULT_SCHEMA_VERSION = "1.0"` — Default version for backward compatibility with legacy contracts.
- Validation for file existence, valid JSON, object payload, and supported schema version.

### Capability Validation

`ProviderCapabilities` in `models/execution.py` defines provider capabilities through:
- An enum `ProviderCapability` with values: `STREAMING`, `WORKSPACE`, `RESUME`, `IMAGES`, `SHELL`, `TESTS`.
- Boolean flags for each capability with automatic synchronization to a `capabilities` set.
- `has_capability()` method supporting both enum and string lookup for backward compatibility.

### Health Checks

The `health_check()` method on adapters verifies:
- Configuration validity (non-positive timeout, invalid settings).
- Authentication status (valid API keys, auth error triggers).
- Workspace availability (target directory exists).
- Provider readiness (unhealthy or rate-limited status).

## Architecture Improvements

### Layered Architecture

The execution layer follows a strict unidirectional dependency model defined in `architecture_rules.py`:

| Layer | Responsibility | Forbidden Dependencies |
|-------|---------------|----------------------|
| Core Utilities | Exceptions, config, logging | Models, execution |
| Domain Models | Pure data structures | Adapters, engine |
| Validation Pipeline | Post-execution checks | Adapters, engine |
| Provider Adapters | Provider-specific logic | Engine |
| Execution Engine | Orchestration | Concrete adapters |

### Adapter Pattern

The `ExecutionAdapter` ABC defines a stable contract that all providers implement. The engine depends only on this abstraction, not on concrete adapter classes.

### Registry Pattern

`ProviderRegistry` provides a centralized, class-variable-based registry for provider adapters and their capabilities. Registration happens at module import time in `factory.py`.

### Validation Pipeline

The `Validator` ABC and `ValidationEngine` provide an extensible validation framework. New validators can be added by subclassing `Validator` and adding to the engine's validator list.

### Provider Abstraction

The engine never imports concrete adapter classes. It uses `AdapterFactory.get_adapter(provider_name)` which returns an `ExecutionAdapter` instance. This ensures provider agnosticism at the architecture level.

### Structured Contracts

Task contracts use a versioned JSON schema with standardized fields: `schema_version`, `task_id`, `project_name`, `workspace_dir`, `task_instruction`, `model`, `timeout`, `acceptance_criteria`, `context`, and `max_retries`.

### Schema Versioning

The contract system supports multiple schema versions through a `SUPPORTED_SCHEMA_VERSIONS` set. Missing version fields default to `1.0` for backward compatibility.

### Architecture Enforcement Tests

`test_architecture.py` uses Python AST parsing to dynamically verify that no module imports forbidden dependencies. The rules are defined declaratively in `architecture_rules.py` and can be extended without modifying the test code.

## Known Limitations

- Only the OpenHands provider has a production `execute()` implementation. The remaining six providers (Claude, Codex, Devin, Cursor, VS Code, Antigravity) are integration-ready scaffolds that support all lifecycle operations except execution.
- The validation pipeline runs Ruff and Pytest as subprocesses. These tools must be installed in the execution environment for validation to succeed.
- Workspace creation uses `shutil.copytree()` which copies the entire source repository. Large repositories may experience slower workspace preparation times.
- The contract schema is currently at version 1.0. Future schema changes will require updating the `SUPPORTED_SCHEMA_VERSIONS` set and adding migration logic.

## Technical Notes

- **ProviderScaffoldAdapter** — Provides default implementations for `prepare()`, `collect_results()`, `cleanup()`, `health_check()`, `_convert_to_contract()`, `load_contract()`, and `_log_provider_activity()`. Subclasses only need to override `execute()` and optionally `_validate_configuration()` and `health_check()`.
- **ExecutionAdapter** — Abstract base class with four abstract methods (`prepare`, `execute`, `collect_results`, `cleanup`) and one optional method (`health_check`).
- **ProviderRegistry** — Class-variable-based registry using a `dict[str, tuple[type[ExecutionAdapter], ProviderCapabilities]]` structure.
- **StructuredProviderLogger** — Writes JSONL entries with schema-validated `StructuredProviderLogEntry` dataclass instances.
- **ValidationEngine** — Runs a configurable list of `Validator` instances, catching individual failures to prevent pipeline crashes.
- **Correlation IDs** — Generated as UUID4 strings at the engine level, propagated through `ExecutionContext`, `ExecutionResult`, `ValidationResult`, and `ExecutionReport`.
- **Contract Schema v1.0** — JSON object with fields: `schema_version`, `task_id`, `project_name`, `workspace_dir`, `task_instruction`, `model`, `timeout`, `acceptance_criteria`, `context` (with `tech_stack`), and `max_retries`.
