# 1. Overview

## Mission
Transform the structured artifacts (Requirements, PRD, Architecture, Task Plan) generated by the Engineering Brain into a physical, runnable software repository.

## Scope
The scope includes project scaffolding, template-based generation, basic code generation boundary definition, and build validation. It explicitly defines the boundary where OpenHands will later take over complex execution.

## Objectives
- Create a physical repository from logical plans.
- Scaffold folders, configuration files, and standard templates.
- Define a strict boundary between AI Engineering Team and execution engines (OpenHands).
- Establish a reproducible build and validation pipeline.

## Deliverables
- Repository Generator Module
- Template Engine Module
- Project Scaffolder Module
- OpenHands Interface Specification
- Build Validation Workflow
- Milestone 2 Sprint Plan

### Engineering Contracts & Specifications
The detailed design boundaries are documented in the following specifications:
- [Milestone 2 State Machine](MILESTONE_2_STATE_MACHINE.md): Lifecycle of repository generation.
- [Template Specification](TEMPLATE_SPEC.md): Structure and parsing rules for tech templates.
- [OpenHands Task Contract](OPENHANDS_TASK_CONTRACT.md): The JSON boundary exchange payload.
- [Milestone 2 API](MILESTONE_2_API.md): Public interfaces for internal modules.

## Non-goals
- Full autonomous code generation (deferred to later milestones/OpenHands).
- Modifying the Engineering Brain (Milestone 1).
- Advanced specialized agents (QA, Security).

## Risks
- Template staleness: Templates (FastAPI, React) may become outdated.
- OpenHands integration complexity: The boundary might leak if not strictly enforced.
- Execution environment inconsistency: Running builds and tests across different OS/environments.

## Success Criteria
- The system can take a `ProjectContext` containing architecture and task plans and generate a fully scaffolded project folder.
- The generated project contains correct configurations (Docker, GitHub Actions, README, ENV).
- Validation workflow successfully runs lint and build steps on the scaffolded project.
- Clear interface for OpenHands is documented and ready for integration.

# 2. Repository Generator Design

## Responsibilities
The Repository Generator acts as the orchestrator for Milestone 2. It reads the Engineering Brain's output and coordinates the Project Scaffolder, Template Engine, and Validation Engine to produce a final repository.

## Input
- `ProjectContext` containing:
  - Architecture decisions (`architecture.json`)
  - Tech stack selection (`tech-stack.json`)
  - Task plan (`task_plan.json`)
  - Idea and Requirements (`requirements.json`)

## Output
- A fully generated project repository at `projects/{project_name}/`.
- A generation report indicating success or validation failures.

## Interfaces
```python
class RepositoryGenerator:
    def generate(self, context: ProjectContext) -> GenerationReport:
        pass
```

## Folder Structure (Platform Side)
- `execution/repository/generator.py`
- `execution/repository/scaffolder.py`
- `execution/templates/engine.py`
- `execution/templates/assets/`

## Generated Files (Project Side)
- `README.md`
- `.gitignore`
- `docker-compose.yml`
- `.env.example`
- `.github/workflows/main.yml`

## Validation
- Verify all required files exist after generation.
- Ensure standard syntax (e.g., valid YAML for docker-compose).

## Acceptance Criteria
- Given a valid `ProjectContext`, the generator produces the corresponding folder structure without crashing.
- Emits a structured `GenerationReport`.

# 3. Template Engine Design

## Where Templates Live
Templates will live in `execution/templates/assets/` organized by technology (e.g., `execution/templates/assets/fastapi/`, `execution/templates/assets/react/`).

## How Templates are Selected
The Template Engine reads the tech stack from the `ProjectContext`. It maps the selected stack (e.g., `backend: fastapi`, `database: postgresql`) to the corresponding template directory.

## How Variables are Injected
We will use **Jinja2** to inject variables.
Variables provided will include:
- `project_name`
- `project_description`
- `database_url`
- `api_port`

## Versioning Strategy
Templates will be versioned within the directory structure:
`execution/templates/assets/fastapi/v1/`
The Tech Stack Selector (from M1) will specify the template version to use.

## Support for Tech Stack
- **FastAPI**: `main.py`, `requirements.txt`, `Dockerfile`.
- **React**: `package.json`, `App.tsx`, `Dockerfile`.
- **PostgreSQL**: `init.sql`, integrated into `docker-compose.yml`.
- **Docker**: `Dockerfile` per service, root `docker-compose.yml`.
- **GitHub Actions**: `.github/workflows/ci.yml` (Build & Test jobs).

# 4. Project Scaffolder Design

## Responsibilities
The Project Scaffolder handles file system operations. It creates physical directories, initializes git, and writes boilerplate configuration.

## Folder Creation
Creates directories based on the architecture (e.g., `backend/`, `frontend/`, `docs/`).

## Configuration Generation
Generates `pyproject.toml`, `package.json`, or equivalent based on the tech stack.

## README Generation
Takes `PRD.md` and `ARCHITECTURE.md` summaries and generates a developer-friendly `README.md`.

## Environment Files
Generates `.env.example` with required keys (e.g., `DATABASE_URL`, `API_KEY`) based on template variables.

## Dependency Files
Generates `requirements.txt` or `package.json` with baseline dependencies required by the templates.

## Git Initialization
Runs `git init`, creates `.gitignore`, and makes an initial commit ("Initial commit by AI Engineering Team").

## Validation
- Verify directory permissions.
- Verify `git status` shows a clean working tree after initialization.

# 5. OpenHands Integration Boundary

## What AI Engineering Team Owns
- Requirements, Architecture, Planning (The "What" and "How").
- Project scaffolding and template initialization (The "Skeleton").
- Defining the tasks for OpenHands.
- Quality Gates (Build, Test, Lint validation).

## What OpenHands Owns
- Executing specific implementation tasks (The "Code").
- File editing, creating implementation logic (e.g., writing route handlers, React components).
- Running terminal commands for debugging within its sandbox.

## Communication Interface
The AI Engineering Team will interact with OpenHands via a clear abstraction layer (API or SDK stub).
```python
class OpenHandsInterface:
    def execute_task(self, task: Task, workspace_dir: str) -> TaskResult:
        pass
```

## Inputs (To OpenHands)
- `workspace_dir`: Path to the scaffolded repository.
- `task_instruction`: The specific task from `task_plan.json`.
- `context`: Relevant architectural context (e.g., "Use FastAPI").

## Outputs (From OpenHands)
- Modified files in `workspace_dir`.
- `TaskResult`: Status (Success/Failure), agent trajectory, and logs.

## Failure Handling
- If OpenHands fails a task, the result is captured.
- The AI Engineering Team evaluates the failure log.

## Retry Policy
- **Max Retries**: 3 per task.
- If failure persists, the task is marked as `FAILED` in the `ProjectContext`, and execution halts for Human Review.

# 6. Build Validation Workflow

The Validation Engine ensures the generated or modified code meets quality standards.

**Workflow Sequence:**
1. **Repository**: Locate the generated workspace.
2. **Dependencies**: Run dependency installation (e.g., `pip install`, `npm install`).
3. **Build**: Run the build step (e.g., `npm run build` or `docker compose build`).
4. **Tests**: Run `pytest` or `npm test`.
5. **Lint**: Run `ruff check` or `eslint`.
6. **Report**: Aggregate all stdout/stderr into a `ValidationReport`.
7. **Ready**: If all steps pass (exit code 0), mark the execution stage as `VALIDATED`.

# 7. Milestone 2 Sprint Plan

Each sprint represents ~1 day of effort.

## Sprint 1: Project Scaffolder
- **Goal**: Create folders and initialize git.
- **Dependencies**: None.
- **Acceptance Criteria**: `ProjectScaffolder` can create a physical folder, `git init`, and write `.gitignore`.
- **Estimated Effort**: 1 Day.

## Sprint 2: Template Engine
- **Goal**: Implement Jinja2 template loading and variable injection.
- **Dependencies**: Sprint 1.
- **Acceptance Criteria**: Can render a `main.py` for FastAPI given context variables.
- **Estimated Effort**: 1 Day.

## Sprint 3: Repository Generator Orchestration
- **Goal**: Connect Engineering Brain output to Scaffolder and Template Engine.
- **Dependencies**: Sprint 1, Sprint 2.
- **Acceptance Criteria**: End-to-end generation of a scaffolded repository from `ProjectContext`.
- **Estimated Effort**: 1 Day.

## Sprint 4: Build Validation Workflow
- **Goal**: Implement the Validation Engine pipeline (Build, Test, Lint).
- **Dependencies**: Sprint 3.
- **Acceptance Criteria**: The system can execute validation commands in the generated workspace and capture exit codes.
- **Estimated Effort**: 1 Day.

## Sprint 5: OpenHands Boundary & Integration
- **Goal**: Implement the `OpenHandsInterface` stub and task dispatch logic.
- **Dependencies**: Sprint 3.
- **Acceptance Criteria**: The system can iterate over tasks and "dispatch" them (mocked) to the OpenHands interface.
- **Estimated Effort**: 1 Day.
